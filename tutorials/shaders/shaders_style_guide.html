Hướng dẫn phong cách viết shader

Hướng dẫn phong cách này liệt kê các quy ước để viết shader gọn gàng. Mục tiêu là khuyến khích viết code sạch, dễ đọc và thúc đẩy sự nhất quán giữa các dự án, các cuộc thảo luận và các bài hướng dẫn. Hy vọng điều này cũng sẽ hỗ trợ việc phát triển các công cụ tự động định dạng.

Vì ngôn ngữ shader của Godot gần với các ngôn ngữ kiểu C và GLSL, hướng dẫn này lấy cảm hứng từ cách định dạng GLSL của chính Godot. Bạn có thể xem ví dụ về các tệp GLSL trong mã nguồn của Godot tại đây.

Hướng dẫn phong cách không phải là bộ quy tắc cứng nhắc. Đôi khi bạn có thể không áp dụng được một số nguyên tắc dưới đây. Khi đó, hãy tự cân nhắc kỹ và hỏi ý kiến các lập trình viên khác.

Nhìn chung, giữ mã nhất quán trong các dự án của bạn và trong nhóm quan trọng hơn việc tuân theo hướng dẫn này đến từng chi tiết.

Ghi chú

Trình chỉnh sửa shader tích hợp của Godot mặc định áp dụng nhiều quy ước này. Hãy để nó hỗ trợ bạn.

Dưới đây là một ví dụ shader hoàn chỉnh dựa trên các hướng dẫn này:

shader_type canvas_item;
// Screen-space shader to adjust a 2D scene's brightness, contrast
// and saturation. Taken from
// https://github.com/godotengine/godot-demo-projects/blob/master/2d/screen_space_shaders/shaders/BCS.gdshader

uniform sampler2D screen_texture : hint_screen_texture, filter_linear_mipmap;
uniform float brightness = 0.8;
uniform float contrast = 1.5;
uniform float saturation = 1.8;

void fragment() {
    vec3 c = textureLod(screen_texture, SCREEN_UV, 0.0).rgb;

    c.rgb = mix(vec3(0.0), c.rgb, brightness);
    c.rgb = mix(vec3(0.5), c.rgb, contrast);
    c.rgb = mix(vec3(dot(vec3(1.0), c.rgb) * 0.33333), c.rgb, saturation);

    COLOR.rgb = c;
}

Định dạng

Mã hóa ký tự và ký tự đặc biệt

  • Dùng ký tự line feed (LF) để xuống dòng, không dùng CRLF hay CR. (mặc định của trình chỉnh sửa)

  • Dùng một ký tự line feed ở cuối mỗi file. (mặc định của trình chỉnh sửa)

  • Dùng mã hóa UTF-8 không có byte order mark. (mặc định của trình chỉnh sửa)

  • Dùng Tab thay vì dấu cách để thụt lề. (mặc định của trình chỉnh sửa)

Thụt lề

Mỗi cấp thụt lề nên nhiều hơn một tab so với khối chứa nó.

Đúng:

void fragment() {
    COLOR = vec3(1.0, 1.0, 1.0);
}

Sai:

void fragment() {
        COLOR = vec3(1.0, 1.0, 1.0);
}

Dùng 2 mức thụt lề để phân biệt các dòng tiếp nối với các khối mã thông thường.

Đúng:

vec2 st = vec2(
        atan(NORMAL.x, NORMAL.z),
        acos(NORMAL.y));

Sai:

vec2 st = vec2(
    atan(NORMAL.x, NORMAL.z),
    acos(NORMAL.y));

Xuống dòng và dòng trống

Về quy tắc thụt lề chung, hãy tuân theo phong cách "1TBS", vốn khuyến nghị đặt dấu ngoặc nhọn của một câu lệnh điều khiển trên cùng một dòng. Luôn dùng dấu ngoặc nhọn cho các câu lệnh, ngay cả khi chúng chỉ có một dòng. Điều này giúp việc refactor dễ hơn và tránh sai sót khi thêm dòng vào câu lệnh if hoặc tương tự.

Đúng:

void fragment() {
    if (true) {
        // ...
    }
}

Sai:

void fragment()
{
    if (true)
        // ...
}

Dòng trống

Bao quanh định nghĩa hàm bằng một (và chỉ một) dòng trống:

void do_something() {
    // ...
}

void fragment() {
    // ...
}

Dùng một (và chỉ một) dòng trống bên trong hàm để phân tách các phần logic.

Độ dài dòng

Giữ mỗi dòng mã dưới 100 ký tự.

Nếu có thể, hãy cố giữ mỗi dòng dưới 80 ký tự. Điều này giúp đọc code trên màn hình nhỏ và khi mở hai shader cạnh nhau trong một trình soạn thảo văn bản bên ngoài, chẳng hạn khi xem một bản sửa đổi dạng diff.

Mỗi dòng một câu lệnh

Không bao giờ gộp nhiều câu lệnh trên cùng một dòng.

Đúng:

void fragment() {
    ALBEDO = vec3(1.0);
    EMISSION = vec3(1.0);
}

Sai:

void fragment() {
    ALBEDO = vec3(1.0); EMISSION = vec3(1.0);
}

Ngoại lệ duy nhất của quy tắc đó là toán tử ba ngôi:

void fragment() {
     bool should_be_white = true;
     ALBEDO = should_be_white ? vec3(1.0) : vec3(0.0);
 }

Khoảng cách trong comment

Comment thông thường nên bắt đầu bằng một dấu cách, nhưng code bị comment lại thì không. Điều này giúp phân biệt comment dạng văn bản với code bị vô hiệu hóa.

Đúng:

// This is a comment.
//return;

Sai:

//This is a comment.
// return;

Đừng dùng cú pháp comment nhiều dòng nếu comment của bạn có thể nằm gọn trên một dòng:

/* This is another comment. */

Ghi chú

Trong trình chỉnh sửa shader, để biến đoạn code đang chọn thành comment (hoặc bỏ comment), nhấn Ctrl + K. Tính năng này thêm hoặc xóa // ở đầu các dòng được chọn.

Comment tài liệu

Dùng định dạng sau cho comment tài liệu phía trên các uniform, với hai dấu sao ở đầu (/**) và dấu sao tiếp theo ở mỗi dòng:

/**
 * This is a documentation comment.
 * These lines will appear in the inspector when hovering the shader parameter
 * named "Something".
 * You can use [b]BBCode[/b] [i]formatting[/i] in the comment.
 */
uniform int something = 1;

Các comment này sẽ hiển thị khi di chuột lên một thuộc tính trong Inspector. Nếu bạn không muốn comment hiển thị trong Inspector, hãy dùng cú pháp comment chuẩn (// ... hoặc /* ... */ với chỉ một dấu sao ở đầu).

Khoảng trắng

Luôn dùng một dấu cách quanh toán tử và sau dấu phẩy. Ngoài ra, tránh các dấu cách thừa trong lời gọi hàm.

Đúng:

COLOR.r = 5.0;
COLOR.r = COLOR.g + 0.1;
COLOR.b = some_function(1.0, 2.0);

Sai:

COLOR.r=5.0;
COLOR.r = COLOR.g+0.1;
COLOR.b = some_function (1.0,2.0);

Không dùng dấu cách để căn thẳng hàng các biểu thức theo chiều dọc:

ALBEDO.r   = 1.0;
EMISSION.r = 1.0;

Số thực dấu phẩy động

Luôn ghi ít nhất một chữ số cho cả phần nguyên và phần thập phân. Điều này giúp dễ phân biệt số thực với số nguyên, cũng như phân biệt các số lớn hơn 1 với các số nhỏ hơn 1.

Đúng:

void fragment() {
    ALBEDO.rgb = vec3(5.0, 0.1, 0.2);
}

Sai:

void fragment() {
    ALBEDO.rgb = vec3(5., .1, .2);
}

Truy cập thành phần của vector

Dùng r, g, b và a khi truy cập thành phần của vector nếu nó chứa một màu. Nếu vector chứa thứ gì khác ngoài màu, hãy dùng x, y, z và w. Điều này giúp người đọc code của bạn hiểu rõ hơn dữ liệu bên dưới đại diện cho điều gì.

Đúng:

COLOR.rgb = vec3(5.0, 0.1, 0.2);

Sai:

COLOR.xyz = vec3(5.0, 0.1, 0.2);

Quy ước đặt tên

Các quy ước đặt tên này tuân theo phong cách của Godot Engine. Phá vỡ chúng sẽ khiến code của bạn xung đột với các quy ước đặt tên tích hợp, dẫn đến code thiếu nhất quán.

Hàm và biến

Dùng snake_case để đặt tên hàm và biến:

void some_function() {
     float some_variable = 0.5;
}

Hằng số

Viết hằng số theo CONSTANT_CASE, tức là viết hoa toàn bộ và dùng dấu gạch dưới (_) để tách các từ:

const float GOLDEN_RATIO = 1.618;

Chỉ thị preprocessor

Các chỉ thị Bộ tiền xử lý shader nên được viết theo dạng CONSTANT_CASE. Các chỉ thị nên được viết mà không có thụt lề phía trước, ngay cả khi lồng bên trong một hàm.

Để giữ dòng thụt lề tự nhiên khi lỗi shader được in ra console, không nên thêm thụt lề bên trong các khối #if, #ifdef hoặc #ifndef:

Đúng:

#define HEIGHTMAP_ENABLED

void fragment() {
    vec2 position = vec2(1.0, 2.0);

#ifdef HEIGHTMAP_ENABLED
    sample_heightmap(position);
#endif
}

Sai:

#define heightmap_enabled

void fragment() {
    vec2 position = vec2(1.0, 2.0);

    #ifdef heightmap_enabled
        sample_heightmap(position);
    #endif
}

Tự động áp dụng định dạng

Để tự động định dạng các tệp shader, bạn có thể dùng clang-format trên một hoặc nhiều tệp .gdshader, vì cú pháp đủ gần với một ngôn ngữ kiểu C.

Tuy nhiên, phong cách mặc định của clang-format không tuân theo hướng dẫn phong cách này, vì vậy bạn cần lưu tệp này dưới tên .clang-format trong thư mục gốc của dự án:

BasedOnStyle: LLVM
AlignAfterOpenBracket: DontAlign
AlignOperands: DontAlign
AlignTrailingComments:
  Kind: Never
  OverEmptyLines: 0
AllowAllParametersOfDeclarationOnNextLine: false
AllowShortFunctionsOnASingleLine: Inline
BreakConstructorInitializers: AfterColon
ColumnLimit: 0
ContinuationIndentWidth: 8
IndentCaseLabels: true
IndentWidth: 4
InsertBraces: true
KeepEmptyLinesAtTheStartOfBlocks: false
RemoveSemicolon: true
SpacesInLineCommentPrefix:
  Minimum: 0 # We want a minimum of 1 for comments, but allow 0 for disabled code.
  Maximum: -1
TabWidth: 4
UseTab: Always

Khi đang ở thư mục gốc của dự án, bạn có thể gọi clang-format -i path/to/shader.gdshader trong terminal để định dạng một tệp shader, hoặc clang-format -i path/to/folder/*.gdshader để định dạng tất cả shader trong một thư mục.

Thứ tự mã

Chúng tôi đề xuất tổ chức code shader theo cách sau:

01. shader type declaration
02. render mode declaration
03. // docstring

04. uniforms
05. constants
06. varyings

07. other functions
08. vertex() function
09. fragment() function
10. light() function

Chúng tôi tối ưu thứ tự này để mã dễ đọc từ trên xuống dưới, giúp các lập trình viên đọc mã lần đầu hiểu cách nó hoạt động, và tránh các lỗi liên quan đến thứ tự khai báo biến.

Thứ tự code này tuân theo hai nguyên tắc chung:

  1. Metadata và thuộc tính trước, sau đó đến các phương thức.

  2. "Public" đứng trước "private". Trong ngữ cảnh ngôn ngữ shader, "public" chỉ những gì người dùng có thể dễ dàng điều chỉnh (các uniform).

Biến cục bộ

Khai báo biến cục bộ càng gần nơi dùng lần đầu càng tốt. Điều này giúp dễ theo dõi mã hơn, không phải cuộn quá nhiều để tìm nơi biến được khai báo.
