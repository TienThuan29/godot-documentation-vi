Lựa chọn về logic

Bạn đã bao giờ băn khoăn nên giải quyết vấn đề X bằng chiến lược Y hay Z chưa? Bài viết này đề cập đến nhiều chủ đề liên quan đến những tình huống khó xử như vậy.

Thêm node và thay đổi thuộc tính: việc nào trước?

Khi khởi tạo node từ script lúc chạy, bạn có thể cần thay đổi các thuộc tính như tên hoặc vị trí của node. Một băn khoăn thường gặp là: khi nào nên thay đổi các giá trị đó?

Cách làm tốt nhất là thay đổi giá trị trên node trước khi thêm nó vào cây scene. Setter của một số thuộc tính có code để cập nhật các giá trị tương ứng khác, và code đó có thể chậm! Trong hầu hết các trường hợp, đoạn code này không ảnh hưởng đến hiệu năng game của bạn, nhưng trong các trường hợp sử dụng nặng như sinh nội dung thủ tục (procedural generation), nó có thể khiến game của bạn chạy ì ạch.

Vì những lý do này, cách làm tốt nhất thường là đặt giá trị ban đầu cho node trước khi thêm nó vào cây scene. Có một số ngoại lệ mà giá trị không thể đặt trước khi thêm vào cây scene, chẳng hạn như đặt vị trí toàn cục (global position).

Load so với preload

Trong GDScript, có phương thức toàn cục preload. Nó nạp resource sớm nhất có thể để dồn các thao tác "nạp" lên trước và tránh phải nạp resource giữa chừng trong đoạn code nhạy cảm về hiệu năng.

Phương thức đối ứng của nó, load, chỉ nạp resource khi chạy tới câu lệnh load. Tức là nó sẽ nạp resource tại chỗ, điều này có thể gây chậm khi xảy ra giữa các quá trình nhạy cảm. Hàm load() cũng là bí danh của ResourceLoader.load(path), thứ mà mọi ngôn ngữ scripting đều truy cập được.

Vậy chính xác thì khi nào preload xảy ra so với load, và khi nào nên dùng cái nào? Hãy xem một ví dụ:

# my_buildings.gd
extends Node

# Note how constant scripts/scenes have a different naming scheme than
# their property variants.

# This value is a constant, so it spawns when the Script object loads.
# The script is preloading the value. The advantage here is that the editor
# can offer autocompletion since it must be a static path.
const BuildingScn = preload("res://building.tscn")

# 1. The script preloads the value, so it will load as a dependency
#    of the 'my_buildings.gd' script file. But, because this is a
#    property rather than a constant, the object won't copy the preloaded
#    PackedScene resource into the property until the script instantiates
#    with .new().
#
# 2. The preloaded value is inaccessible from the Script object alone. As
#    such, preloading the value here actually does not provide any benefit.
#
# 3. Because the user exports the value, if this script stored on
#    a node in a scene file, the scene instantiation code will overwrite the
#    preloaded initial value anyway (wasting it). It's usually better to
#    provide `null`, empty, or otherwise invalid default values for exports.
#
# 4. Instantiating the script on its own with .new() triggers
#    `load("office.tscn")`, ignoring any value set through the export.
@export var a_building : PackedScene = preload("office.tscn")

# Uh oh! This results in an error!
# One must assign constant values to constants. Because `load` performs a
# runtime lookup by its very nature, one cannot use it to initialize a
# constant.
const OfficeScn = load("res://office.tscn")

# Successfully loads and only when one instantiates the script! Yay!
var office_scn = load("res://office.tscn")

using Godot;

// C# and other languages have no concept of "preloading".
public partial class MyBuildings : Node
{
    //This is a read-only field, it can only be assigned when it's declared or during a constructor.
    public readonly PackedScene Building = ResourceLoader.Load<PackedScene>("res://building.tscn");

    public PackedScene ABuilding;

    public override void _Ready()
    {
        // Can assign the value during initialization.
        ABuilding = GD.Load<PackedScene>("res://Office.tscn");
    }
}

using namespace godot;

class MyBuildings : public Node {
    GDCLASS(MyBuildings, Node)

public:
    const Ref<PackedScene> building = ResourceLoader::get_singleton()->load("res://building.tscn");
    Ref<PackedScene> a_building;

    virtual void _ready() override {
        // Can assign the value during initialization.
        a_building = ResourceLoader::get_singleton()->load("res://office.tscn");
    }
};

Preload cho phép script xử lý toàn bộ việc nạp ngay khi script được nạp. Preload rất hữu ích, nhưng cũng có những lúc bạn không muốn dùng nó. Dưới đây là vài điểm cần cân nhắc khi quyết định dùng cái nào:

  1. Nếu không thể xác định khi nào script có thể được nạp, thì preload một resource (đặc biệt là scene hoặc script) có thể dẫn đến những lần nạp thêm ngoài dự kiến. Điều này có thể gây ra thời gian nạp không mong muốn và dài ngắn thất thường, cộng thêm vào các thao tác nạp của script gốc.

  2. Nếu có thứ khác có thể thay thế giá trị (như giá trị khởi tạo được export của scene), thì preload giá trị đó chẳng có ý nghĩa gì. Điểm này không đáng kể nếu bạn luôn định tự tạo script một cách độc lập.

  3. Nếu bạn chỉ muốn 'import' một resource lớp khác (script hoặc scene), thì dùng một hằng số được preload thường là cách tốt nhất. Tuy nhiên, trong những trường hợp ngoại lệ, bạn có thể không muốn làm vậy:

    1. Nếu lớp được 'import' có khả năng thay đổi, thì nó nên là một thuộc tính, được khởi tạo bằng @export hoặc load() (và có thể chưa cần khởi tạo cho đến sau này).

    2. Nếu script cần rất nhiều phụ thuộc, và bạn không muốn tiêu tốn quá nhiều bộ nhớ, thì có thể bạn sẽ muốn nạp và giải phóng các phụ thuộc khác nhau lúc chạy khi hoàn cảnh thay đổi. Nếu bạn preload resource vào hằng số, thì cách duy nhất để giải phóng các resource này là giải phóng toàn bộ script. Nếu chúng được nạp dưới dạng thuộc tính, bạn có thể đặt các thuộc tính này thành null và xóa mọi tham chiếu tới resource (vì là kiểu kế thừa RefCounted, việc này sẽ khiến resource tự xóa khỏi bộ nhớ).

Màn chơi lớn: tĩnh so với động

Nếu bạn đang tạo một màn chơi lớn, hoàn cảnh nào là phù hợp nhất? Tạo màn chơi như một không gian tĩnh duy nhất có tốt hơn không? Hay tốt hơn là nạp màn chơi theo từng phần và thay đổi nội dung thế giới khi cần?

Chà, câu trả lời đơn giản là: "khi hiệu năng đòi hỏi." Băn khoăn giữa hai lựa chọn này là một trong những lựa chọn lập trình kinh điển: tối ưu bộ nhớ hơn tốc độ, hay ngược lại?

Câu trả lời ngây thơ là dùng một màn chơi tĩnh nạp mọi thứ cùng lúc. Nhưng tùy vào dự án, việc này có thể tiêu tốn rất nhiều bộ nhớ. Lãng phí RAM của người dùng khiến chương trình chạy chậm hoặc crash hẳn do mọi thứ khác mà máy tính cố làm cùng lúc.

Dù thế nào, bạn cũng nên chia các scene lớn thành những scene nhỏ hơn (để hỗ trợ tái sử dụng asset). Sau đó lập trình viên có thể thiết kế một node quản lý việc tạo/nạp và xóa/giải phóng resource và node theo thời gian thực. Những game có môi trường lớn và đa dạng hoặc có các thành phần được sinh thủ tục thường triển khai các chiến lược này để tránh lãng phí bộ nhớ.

Mặt khác, viết một hệ thống động phức tạp hơn; nó dùng nhiều logic được lập trình hơn, dẫn đến nhiều khả năng phát sinh lỗi và bug. Nếu không cẩn thận, bạn có thể phát triển một hệ thống làm phình to nợ kỹ thuật của ứng dụng.

Vì vậy, các lựa chọn tốt nhất sẽ là...

  1. Dùng màn chơi tĩnh cho các game nhỏ hơn.

  2. Nếu có thời gian/nguồn lực cho một game vừa/lớn, hãy tạo một thư viện hoặc plugin có thể quản lý node và resource bằng code. Nếu được cải tiến theo thời gian để nâng cao tính dễ dùng và độ ổn định, nó có thể phát triển thành một công cụ đáng tin cậy dùng được qua nhiều dự án.

  3. Dùng logic động cho game vừa/lớn khi bạn có kỹ năng lập trình, nhưng không có thời gian hay nguồn lực để trau chuốt code (game thì phải làm cho xong). Có thể refactor sau này để tách code ra thành một plugin.

Để xem ví dụ về các cách khác nhau để hoán đổi scene lúc chạy, hãy xem tài liệu "Thay đổi scene thủ công".
