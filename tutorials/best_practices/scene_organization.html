Tổ chức scene

Bài viết này đề cập đến các chủ đề liên quan đến việc tổ chức nội dung scene hiệu quả. Nên dùng node nào? Nên đặt chúng ở đâu? Chúng nên tương tác với nhau thế nào?

Cách xây dựng quan hệ hiệu quả

Khi người dùng Godot bắt đầu tự xây dựng scene, họ thường gặp phải vấn đề sau:

Họ tạo scene đầu tiên và lấp đầy nó bằng nội dung, rồi cuối cùng lại tách các nhánh của scene thành những scene riêng khi cảm giác day dứt rằng nên chia nhỏ mọi thứ ngày càng lớn dần. Tuy nhiên, sau đó họ nhận ra rằng những tham chiếu cứng mà trước đây họ có thể dựa vào giờ không còn dùng được nữa. Tái sử dụng scene ở nhiều nơi gây ra vấn đề vì các node path không tìm thấy đích của chúng và các kết nối signal được thiết lập trong trình chỉnh sửa bị hỏng.

Để khắc phục những vấn đề này, bạn phải tạo instance các scene con mà không bắt chúng phải biết chi tiết về môi trường xung quanh. Bạn cần tin tưởng rằng scene con sẽ tự tạo ra chính nó mà không kén chọn cách nó được sử dụng.

Một trong những điều quan trọng nhất cần cân nhắc trong Lập trình hướng đối tượng (OOP) là duy trì các lớp tập trung, chỉ phục vụ một mục đích duy nhất, với liên kết lỏng tới các phần khác của mã nguồn. Điều này giữ cho kích thước đối tượng nhỏ (dễ bảo trì) và tăng khả năng tái sử dụng.

Những thực hành tốt nhất về OOP này có nhiều hệ quả đối với các thực hành tốt nhất trong cấu trúc scene và cách dùng script.

Nếu có thể, bạn nên thiết kế scene sao cho không có phụ thuộc nào. Nghĩa là bạn nên tạo các scene chứa sẵn mọi thứ chúng cần bên trong chính mình.

Nếu một scene buộc phải tương tác với ngữ cảnh bên ngoài, các nhà phát triển giàu kinh nghiệm khuyên dùng Dependency Injection. Kỹ thuật này để một API cấp cao cung cấp các phụ thuộc cho API cấp thấp. Tại sao lại làm vậy? Vì các lớp phụ thuộc vào môi trường bên ngoài có thể vô tình gây ra lỗi và hành vi không mong muốn.

Để làm điều này, bạn phải công khai dữ liệu rồi dựa vào ngữ cảnh cha để khởi tạo nó:

  1. Kết nối tới một signal. Cực kỳ an toàn, nhưng chỉ nên dùng để "phản hồi" hành vi, không dùng để khởi động hành vi. Theo quy ước, tên signal thường là động từ ở thì quá khứ như "entered", "skill_activated" hoặc "item_collected".

    # Parent
$Child.signal_name.connect(method_on_the_object)

# Child
signal_name.emit() # Triggers parent-specified behavior.

    // Parent
GetNode("Child").Connect("SignalName", Callable.From(ObjectWithMethod.MethodOnTheObject));

// Child
EmitSignal("SignalName"); // Triggers parent-specified behavior.

    // Parent
Node *node = get_node<Node>("Child");
if (node != nullptr) {
    // Note that get_node may return a nullptr, which would make calling the connect method crash the engine if "Child" does not exist!
    // So unless you are 1000% sure get_node will never return a nullptr, it's a good idea to always do a nullptr check.
    node->connect("signal_name", callable_mp(this, &ObjectWithMethod::method_on_the_object));
}

// Child
emit_signal("signal_name"); // Triggers parent-specified behavior.

  2. Gọi một phương thức. Dùng để khởi động hành vi.

    # Parent
$Child.method_name = "do"

# Child, assuming it has String property 'method_name' and method 'do'.
call(method_name) # Call parent-specified method (which child must own).

    // Parent
GetNode("Child").Set("MethodName", "Do");

// Child
Call(MethodName); // Call parent-specified method (which child must own).

    // Parent
Node *node = get_node<Node>("Child");
if (node != nullptr) {
    node->set("method_name", "do");
}

// Child
call(method_name); // Call parent-specified method (which child must own).

  3. Khởi tạo một thuộc tính Callable. An toàn hơn phương thức vì không cần sở hữu phương thức đó. Dùng để khởi động hành vi.

    # Parent
$Child.func_property = object_with_method.method_on_the_object

# Child
func_property.call() # Call parent-specified method (can come from anywhere).

    // Parent
GetNode("Child").Set("FuncProperty", Callable.From(ObjectWithMethod.MethodOnTheObject));

// Child
FuncProperty.Call(); // Call parent-specified method (can come from anywhere).

    // Parent
Node *node = get_node<Node>("Child");
if (node != nullptr) {
    node->set("func_property", Callable(&ObjectWithMethod::method_on_the_object));
}

// Child
func_property.call(); // Call parent-specified method (can come from anywhere).

  4. Khởi tạo một tham chiếu tới Node hoặc Object khác.

    # Parent
$Child.target = self

# Child
print(target) # Use parent-specified node.

    // Parent
GetNode("Child").Set("Target", this);

// Child
GD.Print(Target); // Use parent-specified node.

    // Parent
Node *node = get_node<Node>("Child");
if (node != nullptr) {
    node->set("target", this);
}

// Child
UtilityFunctions::print(target);

  5. Khởi tạo một NodePath.

    # Parent
$Child.target_path = ".."

# Child
get_node(target_path) # Use parent-specified NodePath.

    // Parent
GetNode("Child").Set("TargetPath", NodePath(".."));

// Child
GetNode(TargetPath); // Use parent-specified NodePath.

    // Parent
Node *node = get_node<Node>("Child");
if (node != nullptr) {
    node->set("target_path", NodePath(".."));
}

// Child
get_node<Node>(target_path); // Use parent-specified NodePath.

Các lựa chọn này ẩn các điểm truy cập khỏi node con. Nhờ đó node con được liên kết lỏng với môi trường của nó. Bạn có thể tái sử dụng nó trong ngữ cảnh khác mà không cần thay đổi gì thêm ở API.

Ghi chú

Mặc dù các ví dụ trên minh họa quan hệ cha-con, những nguyên tắc tương tự áp dụng cho mọi quan hệ giữa các đối tượng. Các node anh em chỉ nên biết về hệ phân cấp của riêng chúng, trong khi một node tổ tiên làm trung gian cho việc giao tiếp và tham chiếu giữa chúng.

# Parent
$Left.target = $Right.get_node("Receiver")

# Left
var target: Node
func execute():
    # Do something with 'target'.

# Right
func _init():
    var receiver = Receiver.new()
    add_child(receiver)

// Parent
GetNode<Left>("Left").Target = GetNode("Right/Receiver");

public partial class Left : Node
{
    public Node Target = null;

    public void Execute()
    {
        // Do something with 'Target'.
    }
}

public partial class Right : Node
{
    public Node Receiver = null;

    public Right()
    {
        Receiver = ResourceLoader.Load<Script>("Receiver.cs").New();
        AddChild(Receiver);
    }
}

// Parent
get_node<Left>("Left")->target = get_node<Node>("Right/Receiver");

class Left : public Node {
    GDCLASS(Left, Node)

    protected:
        static void _bind_methods() {}

    public:
        Node *target = nullptr;

        Left() {}

        void execute() {
            // Do something with 'target'.
        }
};

class Right : public Node {
    GDCLASS(Right, Node)

    protected:
        static void _bind_methods() {}

    public:
        Node *receiver = nullptr;

        Right() {
            receiver = memnew(Node);
            add_child(receiver);
        }
};

Những nguyên tắc này cũng áp dụng cho các đối tượng không phải Node có phụ thuộc vào đối tượng khác. Đối tượng nào sở hữu các đối tượng khác thì nên quản lý quan hệ giữa chúng.

Cảnh báo

Tuy vậy, bạn nên ưu tiên giữ dữ liệu ở bên trong (nội bộ scene), vì đặt phụ thuộc vào ngữ cảnh bên ngoài, kể cả khi liên kết lỏng, vẫn có nghĩa là node sẽ mong đợi một điều gì đó trong môi trường của nó là đúng. Triết lý thiết kế của dự án nên ngăn điều này xảy ra. Nếu không, những rủi ro vốn có của mã sẽ buộc lập trình viên phải dùng tài liệu để theo dõi quan hệ giữa các đối tượng ở mức vi mô; tình trạng này còn được gọi là "địa ngục phát triển". Viết mã mà phải dựa vào tài liệu bên ngoài mới dùng được an toàn thì mặc nhiên dễ sinh lỗi.

Để tránh phải tạo và duy trì loại tài liệu như vậy, bạn chuyển node phụ thuộc ("node con" ở trên) thành một tool script triển khai _get_configuration_warnings(). Khi hàm này trả về một PackedStringArray không rỗng, Scene dock sẽ hiển thị một biểu tượng cảnh báo cạnh node, với (các) chuỗi đó làm tooltip. Đây cũng là biểu tượng xuất hiện với các node như Area2D khi nó không có node con CollisionShape2D nào. Khi đó trình chỉnh sửa tự mô tả scene thông qua mã script. Không cần lặp lại nội dung trong tài liệu.

Một giao diện người dùng đồ họa (GUI) như thế này có thể thông báo tốt hơn cho người dùng dự án những thông tin quan trọng về một Node. Nó có phụ thuộc bên ngoài không? Các phụ thuộc đó đã được đáp ứng chưa? Các lập trình viên khác, đặc biệt là nhà thiết kế và người viết nội dung, sẽ cần hướng dẫn rõ ràng trong các thông báo cho biết họ phải làm gì để cấu hình nó.

Vậy tại sao toàn bộ màn hoán đổi phức tạp này lại hiệu quả? Bởi vì scene hoạt động tốt nhất khi hoạt động độc lập. Nếu không thể hoạt động độc lập, thì làm việc với các phần khác một cách ẩn danh (với tối thiểu phụ thuộc cứng, tức là liên kết lỏng) là lựa chọn tốt nhì. Sớm muộn gì bạn cũng cần thay đổi một lớp, và nếu những thay đổi đó khiến nó tương tác với các scene khác theo cách không lường trước, mọi thứ sẽ bắt đầu đổ vỡ. Mục đích của toàn bộ sự gián tiếp này là tránh rơi vào tình huống thay đổi một lớp lại gây ảnh hưởng xấu đến các lớp khác phụ thuộc vào nó.

Script và scene, với tư cách là phần mở rộng của các lớp engine, nên tuân thủ tất cả các nguyên tắc OOP. Ví dụ gồm...

  • SOLID:

    • Đơn trách nhiệm

    • Mở để mở rộng, đóng để sửa đổi

    • Thay thế Liskov

    • Phân tách interface

    • Đảo ngược phụ thuộc

  • DRY: Don't Repeat Yourself (Đừng lặp lại chính mình)

  • KISS: Keep It Simple Stupid (Giữ mọi thứ thật đơn giản)

  • YAGNI: You Aren't Gonna Need It (Bạn sẽ không cần đến nó)

Chọn cấu trúc cây node

Bạn có thể bắt đầu làm một game nhưng bị choáng ngợp trước vô vàn khả năng trước mắt. Bạn có thể biết mình muốn làm gì, muốn có những hệ thống nào, nhưng đặt tất cả chúng ở đâu? Cách bạn làm game luôn là do bạn quyết định. Bạn có thể xây dựng cây node theo vô số cách. Nếu chưa chắc chắn, hướng dẫn này có thể đưa ra một mẫu cấu trúc khá ổn để bắt đầu.

Một game luôn nên có một "điểm vào"; một nơi bạn có thể xác định chắc chắn mọi thứ bắt đầu từ đâu để theo dõi logic khi nó tiếp diễn ở những nơi khác. Nó cũng đóng vai trò như góc nhìn toàn cảnh về mọi dữ liệu và logic khác trong chương trình. Với các ứng dụng truyền thống, đây thường là hàm "main". Trong Godot, đó là một node Main.

  • Node "Main" (main.gd)

Script main.gd sẽ đóng vai trò bộ điều khiển chính của game.

Tiếp theo bạn có một "World" trong game (2D hoặc 3D). Nó có thể là con của Main. Ngoài ra, bạn sẽ cần một GUI chính cho game để quản lý các menu và widget mà dự án cần.

  • Node "Main" (main.gd)

    • Node2D/Node3D "World" (game_world.gd)

    • Control "GUI" (gui.gd)

Khi chuyển màn chơi, bạn có thể thay thế các node con của node "World". Chuyển scene thủ công cho bạn toàn quyền kiểm soát cách thế giới game chuyển tiếp.

Bước tiếp theo là xem xét dự án của bạn cần những hệ thống gameplay nào. Nếu bạn có một hệ thống...

  1. theo dõi toàn bộ dữ liệu của nó ở bên trong

  2. cần truy cập được ở phạm vi toàn cục

  3. cần tồn tại độc lập

... thì bạn nên tạo một node autoload 'singleton'.

Ghi chú

Với các game nhỏ hơn, một phương án đơn giản hơn nhưng ít kiểm soát hơn là dùng một singleton "Game" chỉ đơn giản gọi phương thức SceneTree.change_scene_to_file() để thay nội dung của scene chính. Cấu trúc này ít nhiều giữ "World" làm node game chính.

Mọi GUI cũng cần là một singleton, một phần tạm thời của "World", hoặc được thêm thủ công làm con trực tiếp của root. Nếu không, các node GUI cũng sẽ tự xóa khi chuyển scene.

Nếu bạn có các hệ thống sửa đổi dữ liệu của hệ thống khác, bạn nên định nghĩa chúng thành script hoặc scene riêng thay vì autoload. Để biết thêm, xem Autoload so với node thông thường.

Mỗi hệ thống con trong game nên có phần riêng trong SceneTree. Bạn chỉ nên dùng quan hệ cha-con trong trường hợp các node thực sự là thành phần của node cha. Việc xóa node cha có hợp lý dẫn đến việc các node con cũng nên bị xóa không? Nếu không, node đó nên có vị trí riêng trong hệ phân cấp, như một node anh em hoặc một quan hệ khác.

Ghi chú

Trong một số trường hợp, bạn cần các node tách biệt này cũng định vị tương đối với nhau. Bạn có thể dùng các node RemoteTransform2D / RemoteTransform3D cho mục đích này. Chúng cho phép một node đích kế thừa có điều kiện các thành phần transform được chọn từ node Remote*. Để gán target NodePath, hãy dùng một trong các cách sau:

  1. Một bên thứ ba đáng tin cậy, thường là node cha, làm trung gian cho việc gán.

  2. Một group, để lấy tham chiếu tới node mong muốn (giả sử chỉ luôn có một node đích).

Khi nào nên làm điều này là tùy quan điểm. Vấn đề nảy sinh khi bạn phải quản lý chi li thời điểm một node cần di chuyển trong SceneTree để bảo toàn chính nó. Ví dụ...

  • Thêm một node "player" vào một "room".

  • Cần đổi phòng, nên bạn phải xóa phòng hiện tại.

  • Trước khi phòng bị xóa, bạn phải bảo toàn và/hoặc di chuyển player.

    Nếu bộ nhớ không phải là vấn đề, bạn có thể...

    • Tạo phòng mới.

    • Di chuyển player sang phòng mới.

    • Xóa phòng cũ.

    Nếu bộ nhớ là vấn đề, bạn sẽ cần...

    • Di chuyển player sang chỗ khác trong cây.

    • Xóa phòng.

    • Tạo instance và thêm phòng mới.

    • Thêm lại player vào phòng mới.

Vấn đề là player ở đây là một "trường hợp đặc biệt" mà các lập trình viên phải biết rằng họ cần xử lý player theo cách này trong dự án. Cách duy nhất để chia sẻ thông tin này một cách đáng tin cậy trong nhóm là ghi tài liệu cho nó. Lưu chi tiết triển khai trong tài liệu là nguy hiểm. Nó là gánh nặng bảo trì, làm giảm khả năng đọc mã và làm phình to không cần thiết khối kiến thức của dự án.

Trong một game phức tạp hơn với asset lớn hơn, có thể tốt hơn nếu giữ player ở hẳn một chỗ khác trong SceneTree. Điều này mang lại:

  1. Nhất quán hơn.

  2. Không có "trường hợp đặc biệt" nào phải ghi tài liệu và duy trì ở đâu đó.

  3. Không có cơ hội phát sinh lỗi do bỏ sót những chi tiết này.

Ngược lại, nếu bạn cần một node con không kế thừa transform của node cha, bạn có các lựa chọn sau:

  1. Giải pháp khai báo: đặt một Node vào giữa chúng. Vì nó không có transform, chúng sẽ không truyền thông tin này cho các node con của nó.

  2. Giải pháp mệnh lệnh: dùng thuộc tính top_level của node CanvasItem hoặc Node3D. Điều này khiến node bỏ qua transform được kế thừa.

Ghi chú

Nếu làm game mạng, hãy lưu ý node và hệ thống gameplay nào liên quan đến tất cả người chơi, và cái nào chỉ liên quan đến server có thẩm quyền. Ví dụ, không phải người dùng nào cũng cần một bản sao logic "PlayerController" của mọi người chơi - họ chỉ cần của chính mình. Giữ chúng ở một nhánh tách biệt khỏi "world" có thể giúp đơn giản hóa việc quản lý kết nối game và những thứ tương tự.

Chìa khóa để tổ chức scene là xem xét SceneTree theo quan hệ thay vì theo không gian. Các node có phụ thuộc vào sự tồn tại của node cha không? Nếu không, chúng có thể tự hoạt động tốt ở một nơi khác. Nếu có, thì hợp lý là chúng nên là con của node cha đó (và có lẽ là một phần của scene của node cha nếu chưa phải).

Điều này có nghĩa bản thân các node là component không? Hoàn toàn không. Cây node của Godot tạo thành quan hệ kết tập (aggregation), không phải quan hệ hợp thành (composition). Nhưng dù bạn vẫn có sự linh hoạt để di chuyển node, tốt nhất là mặc định không cần phải di chuyển như vậy.
