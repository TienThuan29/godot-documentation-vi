Unit test

Godot Engine cho phép viết unit test trực tiếp bằng C++. Engine tích hợp framework unit test doctest, cho phép viết test suite và test case ngay cạnh mã production, nhưng vì các test trong Godot đi qua một điểm vào main khác, nên các test được đặt trong thư mục riêng tests/, nằm ở thư mục gốc của mã nguồn engine.

Hỗ trợ nền tảng và target

Unit test C++ có thể chạy trên các hệ điều hành Linux, macOS và Windows.

Chỉ có thể chạy test khi bật tools của trình chỉnh sửa, nghĩa là hiện tại không thể test các export template.

Chạy test

Trước khi có thể thực sự chạy test, engine phải được biên dịch với tùy chọn build tests được bật (cùng mọi tùy chọn build khác bạn thường dùng), vì theo mặc định các test không được biên dịch như một phần của engine:

scons tests=yes

Khi build xong, hãy chạy test với tùy chọn dòng lệnh --test:

./bin/<godot_binary> --test

Việc chạy test có thể được cấu hình bằng nhiều tùy chọn dòng lệnh riêng của doctest. Để xem danh sách đầy đủ các tùy chọn được hỗ trợ, hãy chạy lệnh --test với tùy chọn --help:

./bin/<godot_binary> --test --help

Mọi tùy chọn và đối số khác sau lệnh --test đều được coi là đối số cho doctest.

Ghi chú

Các test được biên dịch tự động nếu bạn dùng tùy chọn SCons dev_mode=yes. Nên dùng dev_mode=yes nếu bạn định đóng góp vào việc phát triển engine, vì nó sẽ tự động coi các cảnh báo biên dịch là lỗi. Hệ thống tích hợp liên tục sẽ thất bại nếu phát hiện bất kỳ cảnh báo biên dịch nào, nên bạn nên cố gắng sửa hết các cảnh báo trước khi mở pull request.

Lọc test

Theo mặc định, tất cả test đều được chạy nếu bạn không cung cấp thêm đối số nào sau lệnh --test. Nhưng nếu bạn đang viết test mới hoặc muốn xem output của các assertion thành công từ những test đó để debug, bạn có thể chạy các test cần quan tâm bằng nhiều tùy chọn lọc mà doctest cung cấp.

Cú pháp ký tự đại diện * được hỗ trợ để khớp với số lượng ký tự bất kỳ trong tên test suite, test case và file nguồn:

Tùy chọn lọc

Dạng viết tắt

Ví dụ

--test-suite

-ts

-ts="*[GDScript]*"

--test-case

-tc

-tc="*[String]*"

--source-file

-sf

-sf="*test_color*"

Ví dụ, để chỉ chạy các unit test của String, hãy chạy:

./bin/<godot_binary> --test --test-case="*[String]*"

Có thể bật output của các assertion thành công bằng tùy chọn --success (-s), và có thể kết hợp với bất kỳ tổ hợp tùy chọn lọc nào ở trên, ví dụ:

./bin/<godot_binary> --test --source-file="*test_color*" --success

Có thể bỏ qua các test cụ thể bằng các tùy chọn -exclude tương ứng. Hiện tại, một số test bao gồm các stress test ngẫu nhiên mất khá nhiều thời gian để chạy. Để bỏ qua những loại test đó, hãy chạy lệnh sau:

./bin/<godot_binary> --test --test-case-exclude="*[Stress]*"

Viết test

Test suite tương ứng với các file cài đặt C++, vốn phải bao gồm macro TEST_FORCE_LINK(). Phần lớn test suite nằm trực tiếp trong thư mục tests/.

Tất cả file test đều có tiền tố test_, và đây là quy ước đặt tên mà hệ thống build của Godot dựa vào để phát hiện các test trong toàn bộ engine.

Đây là một test suite tối giản hoạt động được, với một test case duy nhất:

#include "tests/test_macros.h"

TEST_FORCE_LINK(test_string)

namespace TestString {

TEST_CASE("[String] Hello World!") {
    String hello = "Hello World!";
    CHECK(hello == "Hello World!");
}

} // namespace TestString

Ghi chú

Bạn có thể nhanh chóng tạo test mới bằng script create_test.py nằm trong thư mục tests/. Script này tự động tạo một file test mới với mã boilerplate cần thiết ở vị trí thích hợp. Để xem hướng dẫn sử dụng, hãy chạy script với flag -h.

Header tests/test_macros.h gói gọn mọi thứ cần thiết để viết unit test C++ trong Godot. Nó bao gồm các macro assertion và logging của doctest như CHECK đã thấy ở trên, và tất nhiên cả các định nghĩa để viết chính các test case.

Xem thêm

Mã nguồn tests/test_macros.h chứa các macro hiện đã được cài đặt và alias của chúng.

Test case được tạo bằng macro dạng hàm TEST_CASE. Mỗi test case phải có một mô tả ngắn viết trong ngoặc đơn, có thể kèm các tag tùy chỉnh cho phép lọc test lúc chạy, chẳng hạn [String], [Stress], v.v.

Test case được viết trong một namespace riêng. Điều này không bắt buộc, nhưng giúp tránh xung đột tên khi viết các hàm hỗ trợ tĩnh khác cho những quy trình test lặp lại, chẳng hạn như tạo dữ liệu test chung cho từng test, hoặc viết test có tham số.

Godot hỗ trợ viết test cho từng module C++. Để biết cách viết test cho module, hãy tham khảo Viết unit test tùy chỉnh.

Subcase

Trong trường hợp bạn có phần thiết lập chung cho nhiều test case và chỉ khác nhau đôi chút, subcase có thể rất hữu ích. Đây là một ví dụ:

TEST_CASE("[SceneTree][Node] Testing node operations with a very simple scene tree") {
    // ... common setup (e.g. creating a scene tree with a few nodes)
    SUBCASE("Move node to specific index") {
        // ... setup and checks for moving a node
    }
    SUBCASE("Remove node at specific index") {
        // ... setup and checks for removing a node
    }
}

Mỗi SUBCASE khiến TEST_CASE được chạy lại từ đầu. Subcase có thể lồng nhau với độ sâu tùy ý, nhưng bạn nên giới hạn việc lồng nhau không quá một cấp.

Assertion

Danh sách tất cả các assertion thường dùng trong các test của Godot, sắp xếp theo mức độ nghiêm trọng.

Assertion

Mô tả

REQUIRE

Kiểm tra điều kiện có đúng không. Làm toàn bộ test thất bại ngay lập tức nếu điều kiện không đúng.

REQUIRE_FALSE

Kiểm tra điều kiện có sai không. Làm toàn bộ test thất bại ngay lập tức nếu điều kiện đúng.

CHECK

Kiểm tra điều kiện có đúng không. Đánh dấu lần chạy test là thất bại, nhưng vẫn cho phép chạy các assertion khác.

CHECK_FALSE

Kiểm tra điều kiện có sai không. Đánh dấu lần chạy test là thất bại, nhưng vẫn cho phép chạy các assertion khác.

WARN

Kiểm tra điều kiện có đúng không. Không làm test thất bại trong bất kỳ trường hợp nào, nhưng ghi log cảnh báo nếu điều kiện không đúng.

WARN_FALSE

Kiểm tra điều kiện có sai không. Không làm test thất bại trong bất kỳ trường hợp nào, nhưng ghi log cảnh báo nếu điều kiện đúng.

Tất cả assertion ở trên đều có các macro *_MESSAGE tương ứng, cho phép in thông điệp tùy chọn giải thích điều lẽ ra phải xảy ra.

Nên dùng CHECK cho các assertion tự giải thích được và CHECK_MESSAGE cho các assertion phức tạp hơn nếu bạn nghĩ nó cần được giải thích rõ hơn.

Ghi log

Output của test do chính doctest xử lý và hoàn toàn không phụ thuộc vào chức năng in hay ghi log của Godot, nên bạn nên dùng các macro chuyên dụng cho phép ghi log output của test theo định dạng của doctest.

Macro

Mô tả

MESSAGE

In một thông điệp.

FAIL_CHECK

Đánh dấu test là thất bại, nhưng tiếp tục chạy. Có thể đặt trong câu lệnh điều kiện cho các kiểm tra phức tạp.

FAIL

Làm test thất bại ngay lập tức. Có thể đặt trong câu lệnh điều kiện cho các kiểm tra phức tạp.

Có thể chọn các reporter khác nhau lúc chạy. Ví dụ, đây là cách chuyển hướng output sang một file XML:

./bin/<godot_binary> --test --source-file="*test_validate*" --success --reporters=xml --out=doctest.txt

Kiểm thử các nhánh lỗi

Đôi khi, không phải lúc nào cũng có thể kiểm tra một kết quả mong đợi. Với triết lý phát triển của Godot rằng engine không được crash và phải phục hồi êm thấm mỗi khi xảy ra lỗi không nghiêm trọng, điều quan trọng là phải kiểm tra rằng các nhánh lỗi đó thực sự an toàn để chạy mà không làm crash engine.

Hành vi không mong đợi có thể được kiểm tra giống như mọi thứ khác. Vấn đề duy nhất là việc in lỗi sẽ làm output của test bị nhiễu một cách không cần thiết bởi các lỗi đến từ chính engine (ngay cả khi kết quả cuối cùng là thành công).

Để giảm bớt vấn đề này, hãy dùng các macro ERR_PRINT_OFF và ERR_PRINT_ON trực tiếp trong test case để tạm thời tắt output lỗi đến từ engine, ví dụ:

TEST_CASE("[Color] Constructor methods") {
    ERR_PRINT_OFF;
    Color html_invalid = Color::html("invalid");
    ERR_PRINT_ON; // Don't forget to re-enable!

    CHECK_MESSAGE(html_invalid.is_equal_approx(Color()),
        "Invalid HTML notation should result in a Color with the default values.");
}

Các tag đặc biệt trong tên test case

Các tag này có thể được thêm vào tên test case để thay đổi hoặc mở rộng môi trường test:

Tag

Mô tả

[SceneTree]

Bắt buộc cho các test case cần có sẵn scene tree với MessageQueue. Nó cũng bật một rendering server giả lập (mock) và ThemeDB.

[Editor]

Giống [SceneTree], nhưng có thêm hạ tầng liên quan đến trình chỉnh sửa, chẳng hạn EditorSettings.

[Audio]

Khởi tạo AudioServer bằng một audio driver giả lập (mock).

[Navigation2D]

Tạo navigation server 2D mặc định và cung cấp nó cho việc test.

[Navigation3D]

Tạo navigation server 3D mặc định và cung cấp nó cho việc test.

Bạn có thể dùng chúng cùng nhau để kết hợp nhiều phần mở rộng môi trường test.

Test signal

Có thể dùng các macro sau để test signal:

Macro

Mô tả

SIGNAL_WATCH(object, "signal_name")

Bắt đầu theo dõi signal được chỉ định trên đối tượng đã cho.

SIGNAL_UNWATCH(object, "signal_name")

Ngừng theo dõi signal được chỉ định trên đối tượng đã cho.

SIGNAL_CHECK("signal_name", Vector<Vector<Variant>>)

Kiểm tra đối số của tất cả signal đã phát. Vector ngoài chứa từng signal đã phát, còn vector trong chứa danh sách đối số của signal đó. Thứ tự của các signal là quan trọng.

SIGNAL_CHECK_FALSE("signal_name")

Kiểm tra xem signal được chỉ định có không được phát hay không.

SIGNAL_DISCARD("signal_name")

Hủy tất cả bản ghi của signal được chỉ định.

Dưới đây là một ví dụ minh họa cách dùng các macro này:

//...
SUBCASE("[Timer] Timer process timeout signal must be emitted") {
    SIGNAL_WATCH(test_timer, SNAME("timeout"));
    test_timer->start(0.1);

    SceneTree::get_singleton()->process(0.2);

    Array signal_args;
    signal_args.push_back(Array());

    SIGNAL_CHECK(SNAME("timeout"), signal_args);

    SIGNAL_UNWATCH(test_timer, SNAME("timeout"));
}
//...

Công cụ test

Test tool là các phương thức nâng cao cho phép bạn chạy các quy trình tùy ý để hỗ trợ việc test thủ công và debug phần bên trong của engine.

Có thể chạy các công cụ này bằng cách cung cấp tên công cụ sau tùy chọn dòng lệnh --test. Ví dụ, module GDScript cài đặt và đăng ký một số công cụ để hỗ trợ debug tokenizer, parser và compiler:

./bin/<godot_binary> --test gdscript-tokenizer test.gd
./bin/<godot_binary> --test gdscript-parser test.gd
./bin/<godot_binary> --test gdscript-compiler test.gd

Nếu phát hiện bất kỳ công cụ nào như vậy, phần còn lại của các unit test sẽ bị bỏ qua.

Test tool có thể được đăng ký ở bất kỳ đâu trong engine vì cơ chế đăng ký rất giống với cách doctest đăng ký test case bằng kỹ thuật khởi tạo động, nhưng thông thường chúng được đăng ký trong các file nguồn register_types.cpp tương ứng (theo module hoặc core).

Đây là ví dụ về cách GDScript đăng ký test tool trong modules/gdscript/register_types.cpp:

#ifdef TESTS_ENABLED
void test_tokenizer() {
    TestGDScript::test(TestGDScript::TestType::TEST_TOKENIZER);
}

void test_parser() {
    TestGDScript::test(TestGDScript::TestType::TEST_PARSER);
}

void test_compiler() {
    TestGDScript::test(TestGDScript::TestType::TEST_COMPILER);
}

REGISTER_TEST_COMMAND("gdscript-tokenizer", &test_tokenizer);
REGISTER_TEST_COMMAND("gdscript-parser", &test_parser);
REGISTER_TEST_COMMAND("gdscript-compiler", &test_compiler);
#endif

Test tool có thể tự thực hiện việc phân tích dòng lệnh tùy chỉnh với sự trợ giúp của phương thức get_cmdline_args của OS.

Integration test cho GDScript

Godot dùng doctest để ngăn regression trong GDScript trong quá trình phát triển. Có một số loại test script có thể viết:

  • test cho các lỗi mong đợi;

  • test cho các cảnh báo;

  • test cho các tính năng.

Do đó, quy trình viết integration test cho GDScript như sau:

  1. Chọn loại test script bạn muốn viết, rồi tạo một file GDScript mới trong thư mục modules/gdscript/tests/scripts, bên trong thư mục con tương ứng.

  2. Viết mã GDScript. Test script phải có một hàm tên là test() không nhận đối số nào. Hàm này sẽ được test runner gọi. Test không nên có phụ thuộc nào trừ khi phụ thuộc đó cũng là một phần của test. Các lớp toàn cục (dùng class_name) được đăng ký trước khi runner khởi động, nên chúng sẽ hoạt động nếu cần.

    Đây là một ví dụ test script:

    func test():
    if true # Missing colon here.
        print("true")

  3. Chuyển đến thư mục gốc của repository mã nguồn Godot.

    cd godot

  4. Tạo các file *.out để cập nhật kết quả mong đợi từ output:

    bin/<godot_binary> --gdscript-generate-tests modules/gdscript/tests/scripts

Bạn có thể thêm tùy chọn --print-filenames để xem tên file khi output test của chúng được tạo. Nếu bạn đang làm một tính năng mới gây ra crash nghiêm trọng, bạn có thể dùng tùy chọn này để nhanh chóng tìm ra file test nào gây crash và debug từ đó.

  1. Chạy test GDScript bằng:

    ./bin/<godot_binary> --test --test-suite="*GDScript*"

Lệnh này cũng chấp nhận tùy chọn --print-filenames (xem ở trên).

Nếu không có lỗi nào được in ra và mọi thứ suôn sẻ, bạn đã hoàn tất!

Cảnh báo

Hãy đảm bảo output thực sự có các giá trị mong đợi trước khi gửi pull request. Nếu --gdscript-generate-tests tạo ra các file *.out không liên quan đến các test mới thêm, bạn nên hoàn nguyên các file đó và chỉ commit các file *.out cho test mới.

Ghi chú

Test runner của GDScript dùng để test bản cài đặt GDScript, không phải để test script của người dùng hay test engine bằng script. Chúng tôi khuyên bạn nên viết test mới cho các issue liên quan đến GDScript trên GitHub đã được giải quyết, hoặc viết test cho các tính năng hiện đang hoạt động.

Ghi chú

Nếu test case của bạn yêu cầu không có hàm test() trong file script, bạn có thể tắt phần runtime của test bằng cách đặt tên file script sao cho khớp với mẫu *.notest.gd. Ví dụ: "test_empty_file.notest.gd".
